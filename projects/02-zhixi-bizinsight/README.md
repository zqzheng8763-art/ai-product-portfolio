# 「智析 BizInsight」｜电商数据分析 Agent

> **让经营分析从“自己找数、自己想路径、自己做复盘”，变成一次可追溯、可验证的人机协作任务。**

## 这是什么产品？

「智析 BizInsight」是一款面向中小电商运营人员的**经营分析 Agent**。

它不是把传统 BI 搬进聊天框，也不是一个只会生成 SQL 的 ChatBI。产品希望解决的是经营复盘中更高成本的一段工作：用户发现指标异常后，往往还要自己决定“下一步看什么、拆哪个维度、哪些数据能证明、还缺什么证据，以及最后怎么形成复盘结论”。

因此，智析把一次经营分析组织成连续任务：

```text
异常发现
   ↓
贡献拆解
   ↓
关联因素扫描
   ↓
证据判断
   ↓
假设验证
   ↓
复盘摘要
```

Agent 负责分析、验证和组织信息；运营保留最终的经营判断与执行权。

> 本项目的核心不是“让 AI 多说一点”，而是**让 AI 在一个高风险、需要可信数据的业务任务里，知道自己能说什么、不能说什么，以及下一步需要什么证据。**

---

## 为什么做这个产品？

我把问题拆成了三个层次：

### 1. “发生了什么”其实已经不难

Excel、BI 和各种经营看板已经能很好地完成指标查询、趋势查看和维度下钻。

所以智析不应该再把“自然语言查数”当成核心价值。

真正的问题是：

> **当运营看到“销售下降 14.2%”之后，下一步应该看什么？**

### 2. 真正昂贵的是“组织一次分析”

一次经营复盘通常需要不断切换工具：拉数据、透视、看趋势、拆商品 / 渠道、寻找关联指标、人工核对，再把结论整理成汇报材料。

智析的产品机会因此被定义为：

> **降低“分析路径组织”的认知与操作成本，而不是单纯降低取数成本。**

### 3. “可能的原因”不等于“真正的原因”

这是这个项目里我最重要的产品判断之一。

如果 GMV 下滑，同时某商品点击率也下滑，可以说二者**同期变化**，但不能直接说“点击率下降导致 GMV 下降”。

因此产品明确区分：

**事实 → 贡献证据 → 关联证据 → 待验证假设 → 验证路径**

只有证据满足条件，Agent 才继续向下验证；证据不足时，产品宁可告诉用户“数据不足”，也不让模型用确定语气补全一个听起来合理的原因。

## 我做的几个关键产品判断

### 判断一：不做“会聊天的 BI”，而做“分析教练”

传统 BI 更擅长回答：**发生了什么？**

智析希望进一步解决：**我接下来应该分析什么？为什么？还缺什么证据？**

所以产品核心任务不是“问一个数”，而是完成一次经营复盘闭环。

### 判断二：先拆解“谁贡献了变化”，再寻找“为什么变化”

V1.0 不直接做所谓的“因果归因”。

系统先通过确定性计算回答：**整体指标变化主要由哪些商品、渠道或日期贡献？**

例如：

```text
上周 GMV：1000 万
本周 GMV： 860 万
整体下降：140 万

商品 A：下降 60 万
→ 贡献总下降 42.9%
```

此时只能说：

> **商品 A 是主要下降贡献者。**

不能说：

> “商品 A 导致了 GMV 下降。”

贡献拆解还会进行守恒校验，确保各维度贡献可以与总体波动核对，再把主要贡献维度交给后续因素扫描与假设验证。

### 判断三：确定性计算与 LLM 各做自己擅长的事情

我没有让 LLM 直接计算业务数字，而是采用混合架构：

```text
用户自然语言
      ↓
LLM：理解意图 / 组织路径
      ↓
结构化 Analysis State
      ↓
确定性计算工具
      ├─ 指标聚合
      ├─ 趋势计算
      ├─ 环比 / 同比
      └─ 贡献拆解
      ↓
证据层
      ├─ 因素扫描
      ├─ Evidence Gate
      └─ 假设验证
      ↓
LLM：组织解释 / 复盘摘要
```

这样做的本质是：**让模型负责“想怎么分析”，而不是负责“算出一个数字”。**

### 判断四：Human-in-the-loop 不是“人工兜底所有步骤”

我把人工介入放在高风险或信息不足的位置，而不是让用户每一步都确认。

- **字段映射确认**：防止错误字段进入全链路分析
- **证据缺口确认**：决定补充数据、继续看关联因素，还是结束分析
- **最终经营判断**：Agent 不调价、不补货、不投放，只提供事实、证据、假设和低风险验证建议

目标不是降低自动化程度，而是把人的决策权留在真正需要判断的地方。

## V1.0 核心闭环

智析 V1.0 只聚焦一个高价值任务：

> **发现销售异常 → 找主要贡献 → 形成候选原因 → 明确证据与缺口 → 给出下一步验证 → 生成复盘摘要。**

完整用户旅程：

```text
上传销售文件
      ↓
字段识别 / 映射
      ↓
人工确认关键字段
      ↓
数据质量检查
      ↓
用户提出问题
      ↓
Intent 识别 + Analysis State 初始化
      ↓
趋势 / 对比计算
      ↓
异常检测
      ↓
贡献拆解 + 守恒校验
      ↓
因素扫描
      ↓
Evidence Gate
      ├─ 证据充分 → 假设验证
      └─ 证据不足 → 暴露缺口 / 请求补充
      ↓
事实 / 关联证据 / 待验证假设
      ↓
结构化复盘摘要
      ↓
用户最终判断
```

产品同时通过快捷任务入口降低新用户冷启动成本，例如：**看销售趋势、找下滑原因、看商品贡献、看渠道贡献、生成复盘摘要。**

## AI Agent 的工具体系

V1.0 将能力拆为明确的工具，而不是让 LLM 自由发挥：

| 工具 | 作用 | 产品约束 |
| --- | --- | --- |
| `file_parse_upload` | 解析 CSV / Excel 与字段映射推荐 | 关键字段必须人工确认 |
| `data_quality_check` | 检查缺失字段、时间异常、负金额等 | 未通过不得进入分析 |
| `metric_aggregate` | 指标聚合 | 纯代码计算 |
| `trend_compute` | 趋势序列 | 纯代码计算 |
| `comparison_compute` | 环比 / 同比 | 纯代码计算 |
| `contribution_decompose` | 拆解指标波动贡献 | 结果必须可与总体波动核对 |
| `factor_scan` | 扫描关联因素 | 只能生成候选因素 |
| `hypothesis_verify` | 验证简单假设 | 输出“支持 / 不支持 / 证据不足” |
| `nlg_render` | 组织自然语言解释 | 关键数字必须有工具来源 |
| `dashboard_render` | 生成 KPI / 趋势 / 结构展示 | 数字必须与计算结果一致 |
| `report_export` | 形成复盘摘要 / 后续报告导出 | 用户主动触发，敏感明细二次确认 |

## 我如何处理“可信度”

这是一个 AI 产品里比“模型能力”更重要的问题。

### 1. 不让模型直接成为事实来源

用户数据是第一方事实来源；指标口径库保证业务定义一致；领域知识只能用于提出候选解释，不能直接升级为事实。

### 2. 每个关键结论都要能回答“依据是什么”

产品将结论拆成：

| 类型 | 含义 |
| --- | --- |
| **事实** | 确定性计算直接得到的结果 |
| **贡献证据** | 可核对总体波动构成的维度贡献 |
| **关联证据** | 与目标波动同步出现的线索 |
| **待验证假设** | 需要额外数据或比较才能判断的解释 |
| **验证路径** | 下一步应该补什么数据、做什么对比 |

### 3. 数值与语言做一致性校验

评测中要求 NLG 数值与工具结果 100% 吻合；贡献拆解通过守恒误差检验；一旦数值断言出现偏差，直接熔断该段 NLG，回退到确定性模板摘要。

> **宁可少说、不说错。**

## 评测与产品指标

我没有只看“回答得像不像”，而是建立了产品 + 模型 + 安全三层指标。

### 产品价值

- **北极星：有效分析闭环率 / 任务完成率**
- 任务完成时长
- 结论认同率
- 复盘草稿采纳率

### 分析质量

- 关键事实正确率
- 计算一致性
- 贡献分解正确性
- 无证据断言率
- 解释分级质量

### Agent 能力

- 典型经营问题是否能在 ≤2 次交互内进入正确分析路径
- 建议是否低风险、可验证
- Evidence Gate 是否在证据不足时正确停止

### 安全与可控

- 禁止越权执行经营动作
- 禁止跨租户访问
- 禁止数据外泄
- 关键操作审计与二次确认

## 产品如何验证，而不是假装已经验证

目前这份作品**没有虚构用户研究结果**。

核心产品假设仍需要通过真实用户验证：

**H1**：运营在经营复盘中的主要成本是“组织分析路径”，而不仅是取数。  
**H2**：用户更愿意让 Agent 组织分析路径，而不是替自己做经营决策。  
**H3**：确定性计算 + 证据链能够提升信任并降低人工复核成本。  
**H4**：相比直接上传文件给通用大模型，结构化字段映射、可追溯计算和证据链能够带来更稳定的分析结果。

验证设计采用：**半结构化访谈 + 任务可用性测试**。

重点比较同一数据、同一问题下的人工流程与智析流程，观察完成时长、步骤数、追问次数、人工核对次数和复盘材料修改量。

真正应该回答的不是“用户喜不喜欢 AI”，而是：

> **用户是否真的因为智析而少走了几步分析路径，并且更愿意相信它给出的结论。**

```text

文件上传
  ↓
销售异常分析闭环
  ↓
确定性计算 + 贡献拆解 + 证据链
  ↓
验证建议 + 结构化复盘摘要

→ 商品画像
→ 转化漏斗
→ PPT / Word 导出

V2.0
→ 企业数据直连
→ 多店铺聚合

```

核心原则：**先验证一个完整闭环，再扩展更多场景。**

---

## 设计底线

- 只分析、不决策、不执行
- 不做黑箱 NL2SQL
- 不把相关性包装成因果
- 数据不出域
- 证据不足时停止向下推理
- 任何关键数字都必须可追溯、可复核
